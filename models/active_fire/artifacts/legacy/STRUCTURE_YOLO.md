# Базовое решение AF на YOLO — структура

Модуль 1 кейса: детекция активного горения. Только YOLO, без альтернативных
подходов. Ноутбук `baseline_yolo.ipynb` читается сверху вниз, каждая секция
описана ниже.

---

## Состав папки

| файл | что это |
|---|---|
| `baseline_yolo.ipynb` | всё решение: данные → обучение → метрика → submission |
| `submission_yolo.csv` | **выход этого бейзлайна**: 180 AF-строк, маски в RLE |
| `weights/best.pt` | веса после 100 эпох |
| `results.csv` | лог обучения по эпохам |
| `STRUCTURE.md` | этот файл |

**Выход бейзлайна — `baseline_yolo/submission_yolo.csv`.** Ноутбук пишет его в
рабочий каталог под тем же именем. 180 строк, по одной на AF-чип, `class_id` = 1.

---

## Постановка в двух строках

Вход — AF-чип 256×256 на сетке 375 м (покрытие 96×96 км): VIIRS I1–I5 плюс
служебные слои. Выход — бинарная маска, где 1 = пиксель природного горения,
0 = всё остальное. Сдача в RLE.

Метрика соревнования: `Score = 0.35·F1_af + 0.35·IoU_burn + 0.30·mIoU_sev`.
Наша доля — `F1_af`, считается **попиксельно с микро-усреднением**: TP, FP и FN
суммируются по всем чипам в один пул, и только потом берётся F1.

## Разбор по секциям

### 1. Конфигурация
Фиксирует seed для `random`, `numpy`, `torch` и `PYTHONHASHSEED`, задаёт пути и
все константы в одном месте.

Ключевые параметры:

| параметр | значение | почему так |
|---|---|---|
| `UPSCALE = 4` | 256 → 1024 | медианный объект 1×1 px; голова P3 у YOLO работает со stride 8, то есть ячейка предсказаний покрывает 8×8 пикселей входа. Без апскейла цели мельче ячейки в 64 раза и не детектируются в принципе |
| `I4_LO/HI = 270/367` | K | 367 K — точка насыщения канала I4, выше сенсор не различает |
| `D_LO/HI = 0/60` | K | диапазон `I4 − I5` от фона до очага |
| `I3_LO/HI = 0/0.6` | доли единицы | отражение SWIR |
| `BATCH = 2` | | 4 ГБ VRAM при imgsz=1024 |
| `WORKERS = 0` | | multiprocessing-загрузчик torch падает на python 3.14 |
| `VAL_TILE_FRAC = 0.30` | | доля тайлов в валидации |

### 2. Чтение чипа
`load_chip(cid)` возвращает словарь «имя канала → массив 256×256».

**Важно:** имена файлов не соответствуют содержимому. Файл `*_VIIRS_I1-I5.tif`
содержит **8** каналов, а не 5: `I1, I2, I3, I4, I5, solar_zenith, sensor_zenith,
valid`. Файл `*_AUX.tif` содержит **5**: `landcover, dem, t2m, rh2m, wind_speed`.
Поэтому каналы читаются по описаниям из метаданных GeoTIFF, а не по позиции.

Здесь же собирается `meta` с производными колонками: `tile` (пространственное
положение чипа) и `scene` (пролёт × спутник) — они нужны для сплита.

### 3. Метрика организаторов
Класс `MicroF1` накапливает TP/FP/FN по пулу пикселей всех чипов. В конце секции
три ассерта на вырожденных случаях: идеальное предсказание → 1.0, пустое
предсказание при непустом эталоне → 0.0.

**`mAP50`, который печатает ultralytics во время обучения, к этой метрике
отношения не имеет** и ни в один вывод не идёт: он про совпадение боксов, а
оценивают нас по пикселям.

### 4. Потолок box-подхода
Секция считает предел, выше которого детекция боксами не поднимется **в принципе**.

Мысленный эксперимент: пусть детектор идеален — нашёл все объекты, выдал точные
bbox, ничего лишнего. Заливаем каждый bbox целиком и получаем маску.

Результат: `precision = 0.652, recall = 1.000, F1 = 0.789`.

Recall равен единице по построению. Precision упирается в 0.65, потому что
прямоугольник вокруг диагональной цепочки из трёх пикселей захватывает шесть
фоновых. Причина в геометрии объектов: из 3287 связных компонент **41 % состоит
ровно из одного пикселя**, медианный bbox равен 1×1, 76 % боксов не крупнее 2×2.

Это свойство подхода, а не качества модели: тюнинг YOLO потолок не сдвигает.

### 5. Рендер: 13 каналов → 3
YOLO принимает трёхканальное 8-битное изображение. Выбор каналов физический:

| канал | содержимое | зачем |
|---|---|---|
| R | `I4` | основной канал горения: очаг 600–1200 K смещает максимум излучения в средний ИК, контраст к фону на два порядка выше, чем в тепловом I5 |
| G | `I4 − I5` | главный признак: у фона (~300 K) излучение в I4 и I5 сопоставимо, у очага — нет |
| B | `I3` | SWIR-отражение; высокое значение = солнечный блик, то есть **анти**признак |

Два решения, которые легко сделать неправильно:

1. **Нормировка глобальная и фиксированная, а не по каждому чипу.** Per-chip
   нормировка на чипе без огня растянет тепловой шум фона на весь диапазон
   0–255, и модель увидит яркие пятна там, где их нет. Фиксированные пороги
   сохраняют физический смысл: 255 в канале R всегда значит «≥367 K», на любом чипе.
2. **Апскейл только `INTER_NEAREST`.** Билинейная интерполяция усреднит горячий
   пиксель с холодными соседями и занизит пик I4 — ровно тот сигнал, ради
   которого всё делается.

Невалидные пиксели (`valid < 0.5`) гасятся в ноль.

### 6. Разметка: маски → bbox
Каждая связная компонента (8-связность) становится одним объектом класса `fire`.

**Учёт полупикселя:** компонента в пикселе `(row, col)` покрывает квадрат от `col`
до `col+1`, поэтому bbox берётся как `[start, stop]`, а не `[start, stop-1]`.
Иначе объект 1×1 получит нулевую ширину, и ultralytics молча его отбросит.
В конце секции ассерт ровно на этот случай.

### 7. Сплит train/val
Тестовой выборки с масками нет, валидация строится локально.

Организаторы режут public/private «одновременно по территории и по времени».
Авторский ключ группировки `fire_event_id` **пуст во всех 420 строках**
(как и `region`, `landcover_top`), поэтому используется прокси.

**Схема: группировка по тайлу `(epsg, x_min, y_min)`, 30 % тайлов в val.**
Ни один тайл не встречается по обе стороны — это проверяется ассертом.

Почему не двойная блокировка (тайл + сезон): она измерялась и оставляет
6–37 чипов в валидации, выбрасывая до половины набора. На таком val разница
между вариантами модели тонет в шуме.

Почему остаётся пересечение по сценам: **все 78 сцен покрывают более одного
тайла**, полностью развести тайлы и сцены одновременно нельзя без потери половины
данных. Ноутбук печатает это число явно. Следствие: локальная цифра слегка
оптимистична относительно private, но сравнению вариантов между собой не мешает.

Опасность, которую схема закрывает: постоянные термоаномалии (газовые факелы)
привязаны к местности, и при случайном сплите модель запоминала бы их положение.

### 8. Экспорт в формат ultralytics
Создаёт структуру `work/yolo_ds/{images,labels}/{train,val}` и `data.yaml`.

124 чипа без огня не выбрасываются: для них пишется **пустой** `.txt`.
Ultralytics принимает это как валидную разметку и использует их как
отрицательные примеры. Для задачи, где узкое место — precision, это существенно.

### 9. Обучение
`yolo11n.pt`, 100 эпох, imgsz 1024, batch 2, seed 0, `deterministic=True`.

**Все аугментации выключены явным списком**, а не значением по умолчанию:
`hsv_h/s/v`, `degrees`, `translate`, `scale`, `shear`, `perspective`,
`flipud`, `fliplr`, `mosaic`, `mixup`, `copy_paste`, `erasing` — все в ноль.

Причины: `mosaic` склеивает четыре чипа в один, что ломает и без того хрупкий
масштаб объектов в 1–2 пикселя; `hsv_*` меняет яркость, а каналы у нас —
физические величины (яркостная температура в кельвинах), и сдвиг яркости
означает «пожар стал холоднее», то есть порождает физически невозможные примеры.

Ячейка переиспользует готовые веса, если `work/runs/af_yolo/weights/best.pt`
уже существует, иначе запускает обучение.

### 10. Оценка
`boxes_to_mask` переводит предсказание YOLO в бинарную маску 256×256: координаты
делятся на `UPSCALE`, каждый бокс заливается целиком. **Именно здесь теряется
precision** — это то самое место, которое упирается в потолок из секции 4.

Порог уверенности `conf` подбирается сеткой по val. Это единственный
настраиваемый гиперпараметр: при доле горящих пикселей 0.035 % дефолтный
`conf = 0.25` заведомо не оптимален.

Итог печатается тремя числами: потолок подхода, бейзлайн, тривиальный ответ.

### 11. RLE
`rle_encode` / `rle_decode` по правилам постановки:

- пиксели нумеруются **построчно**, слева направо и сверху вниз, **с единицы**;
- пары «начальный пиксель — длина» по возрастанию;
- серии не пересекаются и не соприкасаются;
- пустая маска → пустая строка, не NaN.

⚠️ Нумерация **построчная** (C-order). Во многих соревнованиях RLE считается по
столбцам (Fortran) — перепутать значит получить формально валидный, но
бессмысленный файл. Проверка round-trip гоняется на всех 420 масках побитово.

### 12. Инференс на тесте
Состав чипов берётся из `sample_submission.csv`, а не из файлов на диске:
постановка требует полного совпадения набора пар `(chip_id, class_id)` с шаблоном.

Тестовые растры лежат в `<test>/af/viirs` и `<test>/af/aux`, метаданные
обезличены (остались только `chip_id, kind, width, height, gsd, valid_frac,
cloud_frac`). Рендер — та же функция с теми же фиксированными константами: на
тесте нет ни масок, ни статистик обучающей выборки.

Перед записью — четыре проверки: нет NaN, `class_id` всегда 1, число строк
совпадает с числом AF-чипов, набор `chip_id` совпадает с шаблоном.

## Результаты

| | F1_af |
|---|---|
| потолок box-подхода (оракул на идеальных боксах) | 0.7892 |
| **YOLO-det бейзлайн** | **0.4176** |
| тривиальный ответ «всё ноль» | 0.0000 |

Реализовано 53 % от потолка подхода. Лучшая точка: precision 0.2836,
recall 0.7920, порог `conf = 0.5`.

Сплит: train 323 чипа (7004 px горения), val 97 чипов (2721 px),
0 общих тайлов.

На тесте предсказано 9246 пикселей на 180 чипов — 51 на чип против 23 на чип
в эталоне обучающей части. Переразметка примерно вдвое ожидаема и объясняется
заливкой боксов при precision 0.28.

## Ограничения

1. **Потолок 0.789** заложен в выбор подхода и тюнингом не лечится.
2. **Техногенные термоаномалии не фильтруются вообще.** Постановка требует
   отделять газовые факелы от природного горения, а по одиночному снимку они
   неотличимы — различает их только повторяемость по многолетнему архиву.
3. **Из 13 доступных каналов используются 3.** Не задействованы `I1`, `I2`,
   `solar_zenith`, `sensor_zenith`, `landcover`, `dem` и метео.

## Воспроизводимость

`seed = 0` зафиксирован для `random`, `numpy`, `torch` и ultralytics
(`deterministic=True`). Сплит детерминирован от того же seed. Нормировка каналов
задана константами и не зависит от содержимого конкретного чипа, поэтому
одинаково применяется к train, val и тесту.

Окружение: python 3.14, torch 2.11.0+cu128, ultralytics 8.4.155, rasterio 1.5.1,
opencv 5.0.0, numpy 2.5.2, pandas 3.0.5, scipy 1.18.1.

## Формат выхода

**Выход модуля — `submission_yolo.csv`.** Каждая строка содержит маску одного
AF-чипа, закодированную в RLE:

    chip_id,class_id,rle
    AF_te_000001,1,5036 6 5292 6 5548 6 ...

180 строк, по одной на AF-чип, `class_id` всегда 1. Никаких промежуточных
форматов нет: RLE в CSV — единственный выход.

Что делает секция 12 перед записью:

- состав чипов берётся из `sample_submission.csv`, а не из файлов на диске —
  постановка требует полного совпадения набора `chip_id` с шаблоном;
- четыре проверки: нет NaN, `class_id` всегда 1, число строк равно числу
  AF-чипов, набор `chip_id` совпадает с шаблоном.

Объединение с масками второго модуля здесь не делается — это происходит
в приложении после получения результатов обоих слоёв.
